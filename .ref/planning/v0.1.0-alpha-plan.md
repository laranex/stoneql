# StoneQL v0.1.0 Alpha — implementation plan (macOS, MySQL/MariaDB)

**Status: Proposed / awaiting approval** (2026-10-26). Planning only: no code, test, vendor, Cargo or package file was changed to write this plan, and no acceptance test below has been executed. Scope comes from **D022** and **D021** (Approved product decisions, `architecture-decisions.md`). Everything else here — task breakdown, sizes, minimal slices, numerical values, interpretations — is Proposed unless labelled otherwise.

Labels used: **Approved** (recorded user decision) · **Implemented-verified** (committed code with recorded fixture evidence; still not release evidence) · **Draft** (uncommitted working-tree code, unreviewed, no recorded evidence) · **Proposed** · **Deferred** · **Unresolved blocker**.

## Scope (Approved, D022)

- macOS Apple Silicon first; MySQL 8.4 / MariaDB 11.4 primary engines (fixture versions; exact supported versions Proposed).
- Usable client: live browsing, CRUD, safe SQL execution, SSH, basic SQL/CSV import/export.
- PostgreSQL optional; Windows, Linux, SQLite, advanced objects, XLSX import deferred (code stays, outside alpha claims).
- Signed and notarized DMG; separate desktop/server release gates; Rust core independent of macOS APIs; budgets recorded for approval.

## Workstream order and dependencies

```text
(a) M005 blockers ─────────────────────────────────────────────┐
(e) metadata-limit decision ─┐                                  │
(b) M006 execution reconcile + safe SQL ──┬─> (c) browse + CRUD ─┼─> (g) M010-D evidence ─> M009 sign-off

(f) M009 packaging/signing/DMG (approvals start now; build after D023) ──────┘
```

(a), (e) and the approval half of (f) can start immediately and in parallel. (c) needs (b)'s job/outcome contract and schema DTOs; (d) needs (b) writes and (c) metadata. (g) binds everything to the signed artifact. Sizes: S ≤ 1 day, M 2–4 days, L ≥ 1 week of focused work (Proposed estimates, single implementer).

## Remaining approval decisions (ranked by risk)

1. **Generated-write gating interpretation** (D022 bullet): may single-row CRUD and CSV import ship before MySQL write cancellation and SSH cancel-slot exhaustion are resolved, or do all writes wait? Risk: silent committed writes reported as cancelled. Recommendation: all writes wait for b4/b5 (they are small).
2. **v1 contract versioning for job/lease/outcome DTOs** (m006 prerequisite 1) and the exact cancellation-vs-unknown DTO mapping. Risk: misreported data outcomes.
3. **Metadata-limit vendor patch** (e1: 4,096 vs 16,384 columns, 4 MiB). Risk: process abort from a hostile/misbehaving server.
4. **CRUD optimistic-check policy**: changed-columns vs all-columns compare; no-PK tables browse-only; found-vs-changed rows semantics. Risk: lost updates.
5. **SQL import semantics**: per-statement autocommit, stop-on-first-error, refused statements list, snapshot semantics for SQL export. Risk: partial imports misreported.
6. **F-01 native store mechanism** (Keychain item vs app-data file) and remaining M005 review items 3–7. Risk: trust anchor tampering / data location tied to D023.
7. **Numerical limits and budgets** (table above), including whole-app RSS and transport budgets. Risk: unbounded resource use; release cannot be signed off without them.
8. **Bundle identifier (D023)** before the first signed build. Risk: stranded Keychain/profile data after release.
9. **Signing and notarization custody**, Apple Developer Team, minimum macOS version, x86_64 inclusion. Risk: compromised signing identity; unsupported OS installs.
10. **Linux GTK advisory risk acceptance or exclusion evidence** for the macOS artifact. Risk: audit gate.
11. **PostgreSQL inclusion** (go/no-go at feature freeze) and SQLite UI gating method (hide vs label). Risk: unsupported claims.
12. **GZIP export / GZIP import deferral**, CSV library choice. Risk: expansion bombs (import only).
13. **Updater: none; App Sandbox: no; data-protection Keychain** (M005 review item 4). Risk: low for alpha; revisit before beta.

Requires migration code (profile export/import or a native reader of another app's WebKit store — fragile, internal format) plus Keychain re-save, and release-note instructions. High cost, permanent legacy paths |

### Recommendation (Proposed)

1. **Decide the final identifier before the first signed build** (f1). If the project controls a domain for StoneQL, use a reverse-DNS identifier under it; otherwise keep `app.dbadmin.desktop` permanently and treat the legacy name as cosmetic. Do not invent a domain on the user's behalf.
2. If it changes: in one reviewed commit change `tauri.conf.json` `identifier`, `DEFAULT_SERVICE` (Proposed: `<identifier>.credentials`, keeping one naming source), the test prefix and the assertion, and the docs above. Do not write migration code.
3. Developer reset steps (document, do not automate): delete old items with `security delete-generic-password -s app.dbadmin.desktop.credentials` repeated until none remain (verify with `security find-generic-password -s app.dbadmin.desktop.credentials`); remove `~/Library/WebKit/{stoneql-desktop,dbadmin-desktop}` and `~/Library/Caches/stoneql-desktop` if desired; re-create profiles.
4. After the first public alpha, freeze the identifier, signing Team and Keychain service; any later change needs its own migration plan and approval.
5. Verify on the first bundled build which `~/Library` paths the identifier actually keys (record in M009 evidence) before writing the uninstall/cleanup instructions.
