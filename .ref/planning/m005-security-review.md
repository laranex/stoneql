# M005 security review — SSH transport and macOS Keychain secret references

**Status: independent review, findings only. Proposed / awaiting approval.** Nothing here approves D016–D020, a signing identity, an OS/auth-method matrix or transport budgets.

- Reviewer constraints: review only. No code, tests, docs, milestone or decision files were changed, and no git writes were made. This file is the only artifact.

## Executive summary

The M005 core holds up. Host keys are compared exactly by key data, and a missing key is refused before any network I/O. A changed key always fails hard; there is no TOFU path and no trust-all path. Host certificates are refused. The negotiated set has no SHA-1 MAC and no CBC cipher, and strict-kex (Terrapin) is on. RSA cannot be used because the `rsa` crate is not in the lockfile, but RSA is still advertised in the host-key preference list (see F-06). TLS to the database is preserved through the tunnel. The sqlx sources confirm that MySQL `VerifyIdentity` and PostgreSQL `VerifyFull` still upgrade TLS over the Unix socket and verify against `options.host`. The fixture shows this too. IPC is strictly decoded and bound to the main window, origin and session. No command returns a secret, and errors are mapped to fixed codes. `cargo audit` (advisory DB fetched 2026-10-26) reports **0 vulnerabilities**, and the lockfile contains no `rsa` crate. I re-ran `npm run test:ssh` on the clean snapshot and it passed for all three engines with complete cleanup.

The main weaknesses are about *where trust lives* and *what happens at the edges*:

1. **The SSH trust anchor is renderer-owned (D017).** The enrolled host key is stored in the renderer's localStorage and sent with every connect request. Native code checks the server against whatever key the renderer sends. Nothing native binds a key to `host:port`, and the Keychain scope for SSH secrets does not include the host key. A compromised renderer (XSS), combined with a network attacker, could therefore swap the key and capture the SSH password. Today's strict CSP and local-only origin make this hard to exploit. It is still the largest gap against the stated model that the renderer is less trusted than native code.
2. **Cancellation and timeouts do not cover Keychain resolution.** Saved secrets are resolved before the cancellable, deadline-bounded setup begins, and this step can block on a Keychain prompt. `cancel_connect` is silently ignored during that phase. If the renderer's 8 s timeout fires, native code still finishes the connect and registers a handle that the renderer never learns about. That handle holds one of 8 slots, plus a live SSH session, for up to one hour.
3. **A dead tunnel keeps its slot until expiry.** Detection already exists (russh keepalive 30 s × 3). Only the automatic release is missing.

None of these is Critical. I recommend fixing F-02, F-03 and F-04 before the macOS alpha, because they are small and cause user-visible resource exhaustion and confusing behaviour. F-01 can ship in the alpha **only with an explicit, recorded risk acceptance**; the preferred fix is native-side enrollment.

Checked and found sound (no finding): strict envelope round-trip decoding rejects unknown fields such as `privateKey`, `path` and `forwardAgent` (`v1.rs:96-122`, though this is not asserted by a test, see below). `guard()` enforces the main window and local origin (`lib.rs:106-117`), and every new command calls `authorize()`. Capabilities are main-window only and grant no fs/shell/dialog plugin (`capabilities/main-window.json`, `build.rs`). Key-file grants are typed and owner-scoped, and are revoked on reset/shutdown (`lib.rs:401-443,596,608`). The agent is used only for signing, is dropped after auth, tries ≤5 non-RSA identities, sends no forwarding/session requests (fixture: 0 `session`, 0 `auth-agent-req`), and its socket comes from `SSH_AUTH_SOCK` at startup and never over IPC (`lib.rs:36-43`). Channels are only `direct-tcpip` to the profile's DB host (`ssh.rs:373-387`). The endpoint dir uses `DirBuilder::create` with mode 0700, so it fails if the path exists and there is no pre-creation or symlink race. Its name carries 64 random bits. Errors use fixed strings and codes, and no logger is installed. Setup failure, cancellation and drop release the permit, attempt guard, tunnel and dir (fixture: 100 cycles, 0 tunnels, 0 pending, 0 dirs, fds 7→7). Default russh algorithms: ML-KEM/curve25519 kex, chacha20/AES-GCM/AES-CTR, ETM SHA-2 MACs, no SHA-1 MAC, strict-kex.

## Doc vs. code discrepancies

1. **User guide** (`docs/user-guide/connections.md`): "Cancel connecting stops the setup without leaving a tunnel behind." This is not true while a Keychain reference is being resolved (F-02), or after a renderer timeout, which leaves an orphan handle and tunnel.
2. **User guide**: "Unticking the option or removing the profile forgets the saved secret." Delete failures are swallowed, and browser-mode removal skips deletion (F-10).
3. **D018** (`architecture-decisions.md:85`): "so no other local user/process can reach the endpoint." Same-user processes can reach it (F-11).
4. **D016**: "RSA user and host keys are unsupported (explicit `UNSUPPORTED_CAPABILITY`)." True for user key files only. RSA agent identities are skipped silently, and RSA host keys surface as `Unavailable`/connection failed (F-07).
5. **ssh-credentials.md "Lifecycle"**: "Setup is bounded (SSH phase within the 3 s deadline, whole setup within 6 s)." Secret resolution (a Keychain prompt) and key-file reading happen before and outside that bound (F-02).
6. **ssh-credentials.md "Native commands"**: "a `privateKey`, `path` or `forwardAgent` field is rejected." This is true by strict round-trip decoding but has no dedicated test.
7. **`postgres.rs:28` comment**: "A leading slash selects a Unix socket, which bypasses TLS verification entirely." This is inaccurate for sqlx 0.9. TLS is still requested over sockets; this is the property the SSH tunnel relies on. The refusal of `/` hosts is still correct, because the hostname would be a path. Fix the comment to avoid future confusion.
8. **ssh-credentials.md**: "A tunnel whose SSH session dies (keepalive exhausted) makes the handle report disconnected." Plausible from code (`usable()` plus the russh keepalive error), but **untested**.
9. The docs are otherwise accurate and appropriately hedged. Memory erasure, the 8 s prompt risk, dead-tunnel slots and macOS-only status are all disclosed.

7. RSA-only sshd and RSA agent identity → expected error code (F-07). P-384/P-521 key files.

## Decisions requiring human approval (ranked by risk)

1. **F-01: where the enrolled host key lives.** Choose between (a) native enrollment store (recommended), (b) the interim fix that binds Keychain scopes to the host-key fingerprint, or (c) recorded risk acceptance for alpha on the basis of strict CSP and local-only content.
2. **F-02/F-03: blocking or acceptance for alpha.** These are recommended as alpha blockers because the fixes are small. If deferred, record the 1 h slot-loss behaviour in the release notes.
3. **RSA policy** (stay unsupported vs. signing-only risk acceptance vs. `aws-lc-rs`) and **keyboard-interactive** support or explicit detection.
4. **Code-signing identity and Keychain ACL / data-protection keychain** (`kSecUseDataProtectionKeychain` + `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` require a signed app and entitlements). Signing and publishing must not be inferred from implementation authorization (AGENTS.md).
5. **russh upgrade policy** (pin plus review window plus advisory-triggered upgrade) and the cadence for watching advisories.
6. **D018 same-user reachability** (peer-PID check) and the crash-sweep behaviour.
7. **G4/G5 transport budgets.** Overhead is only characterized (debug build, Docker loopback); the budget is unapproved.
