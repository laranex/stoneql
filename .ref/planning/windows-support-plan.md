# Windows desktop support — plan (branch `windows-support`, started 2026-11-17)

**Status: Proposed / in progress. No Windows claims in docs, README or releases until the release gates below pass.** Related gates: `.ref/ms/M004`, `M005`, `M009` (Deferred Windows items), D016–D020 (SSH), D005 (secrets).

## Current state (inventory 2026-11-17)

Most Unix-only code is already `cfg`-gated with non-Unix fallbacks, so a Windows build is expected to compile, but it would be badly limited:

| Area | Today on Windows | Code |
| --- | --- | --- |
| SSH tunnel | Refused (`Unsupported`): the local endpoint is a Unix socket and the drivers connect via `socket` | `crates/stoneql-runtime/src/ssh.rs` (`bind`, `#[cfg(not(unix))]`) |
| SSH agent | Unix socket (`SSH_AUTH_SOCK`) only; Windows agents use named pipes | `ssh.rs`, host `agent_socket` |
| Outcome journal | Fail-closed stub (`Unavailable`), so **read-write is refused** | `execution/journal.rs` (`#[cfg(not(unix))] impl Store`) |
| Saved passwords | `OsSecretStore` returns `Unsupported` | `apps/desktop/src-tauri/src/secrets.rs` |
| Host keys / transfer temp files | Fallbacks without owner-only permissions | `host_keys.rs`, `transfer.rs` |
| Web content crash handler | macOS only | `lib.rs` (`on_web_content_process_terminate`) |
| Packaging | ad-hoc macOS scripts use POSIX shell syntax (`$HOME`, inline `RUSTFLAGS=`) | `package.json` `desktop:*:adhoc` |
| Real-server tests | Docker Linux containers; not available on Windows runners | `tools/test-*.mjs` |

## Phases

1. **Build and CI facts (no product decision).** Gate Unix-only tests; non-gating `windows-2025` CI job on this branch whose steps continue after failures; run it by manual dispatch. Outcome: the complete list of compile/test failures.
2. **Credential store.** User preference (2026-11-17): save passwords "in user home dir with encryption". Implemented on the branch (`secrets/dpapi.rs`, unverified until the Windows CI run passes): one file per reference at `%APPDATA%\me.thixpin.stoneql.credentials\<reference>.bin`, encrypted with **DPAPI** (`CryptProtectData`, current-user scope, no UI) with the service and reference as entropy so a file copied to another reference does not decrypt; atomic temp-file + rename; the same scope binding as the Keychain items. Only `%APPDATA%`'s default per-user ACL protects the files. Limitation to document: DPAPI has no per-app ACL — any process running as the user can decrypt (Credential Manager is the same and caps blobs at 2,560 bytes, below `MAX_SECRET_BYTES` 16,384). Dependency: `windows-sys =0.61.2` (already in the lockfile via Tauri/tokio). **Approved 2026-11-17 (user): the DPAPI calls live in a new ~90-line crate `crates/stoneql-dpapi`, the workspace's only exception to `unsafe_code = "forbid"`** (`deny` plus a single `#[allow]` on the FFI function, `undocumented_unsafe_blocks = "deny"`, compiled only on Windows). `tests/workspace.test.mjs` fails if any other member stops inheriting the workspace lints or mentions `unsafe_code`.
3. **Outcome journal on Windows.** Keep the fail-closed stub until a port gives the same guarantees: no reparse-point following, single-process lock, atomic replace (`ReplaceFileW`/`MoveFileExW` with write-through), owner-only location. Then read-write can be enabled on Windows.
   - **2026-11-17 (user chose "journal port first" before the remote fixture):** safe-`std` port written (`execution/journal/windows.rs`, tests in `journal/windows_tests.rs`; J1–J11 ungated on Windows except J4, which changes Unix permissions). Mechanisms: `FILE_FLAG_OPEN_REPARSE_POINT` on every open and reparse/type checks (refused as `Insecure`); the directory held open without `FILE_SHARE_DELETE` for the journal's lifetime instead of `openat`; `File::try_lock` (LockFileEx); `create_new` temp → flush → `fs::rename` (atomic replace, short retry on sharing violations) → flush the journal file; quarantine by hard link while the read file is held without delete sharing. Cross-linted clean for `x86_64-pc-windows-gnu` on the Linux server (MinGW); **not yet run on Windows**.
   - **Accepted gaps (user, 2026-11-17: "accept and document"; closing them would widen the `unsafe` exception):** (1) no ownership/ACL check, so `Insecure` for a foreign owner or loose ACL is not detected (relies on the profile's default ACL); (2) no directory fsync / write-through rename, so durability of the rename across power loss is not guaranteed. Also: an earlier damaged copy is not reused (no stable file identity in `std`). Windows CI run 44101214401 (2026-11-17): all nine Windows store tests pass, including that renaming the journal directory and its **parent** is refused while the journal is open; J1–J11 pass except J7, which read the open journal's lock file (Windows locks are mandatory; test fixed to skip it). Run 44103890341 on 3cbe7a8: 162 Rust tests pass, 0 fail (all nine store tests and J1–J11 except J4); only the non-gating full `cargo audit` fails. **Phase 3 met on CI; read-write is enabled on Windows with the accepted gaps.**
4. **SSH tunnel endpoint (decision needed).** Finding (2026-11-17): both vendored drivers verify TLS against `options.host` (`vendor/sqlx-mysql/src/connection/tls.rs:64`, `vendor/sqlx-postgres/src/connection/tls.rs:57`) and connect to `options.socket` when set, else `(host, port)` (`establish.rs:18`, `stream.rs:47`). sqlx-core's `connect_uds` is Unix-only. So neither option works without a vendored-driver patch:
   - (a) **Loopback TCP listener** (`127.0.0.1:<random>`) plus a small vendor patch adding a "connect address" separate from `host`, so TLS still verifies the database name. Drawback: unlike the owner-only Unix socket directory, any local process or user can connect to the port while the tunnel is open; mitigating that (check the peer's owning process with `GetExtendedTcpTable`) adds Windows-specific code.
   - (b) **No listener: in-process stream.** Vendor patch adding an option that supplies the connection stream; StoneQL implements `sqlx_core::net::Socket` (public trait) over the SSH channel. No local exposure on any OS, and the tunnel could later use it on macOS/Linux too. Larger patch (both drivers) and more review.
   - Recommendation: (b), because (a) opens a local port to every process on the machine. Security decision for the user. Agent auth: Windows OpenSSH agent (named pipe) first, Pageant second; OpenSSH-format keys (`.ppk` via PuTTYgen conversion documented). No external PuTTY dependency: the built-in client (russh) is used on all platforms.
5. **Packaging.** Installer format (NSIS vs MSI), WebView2 delivery, unsigned-binary SmartScreen warnings (Authenticode signing deferred like Developer ID), Windows build scripts.
6. **Verification standard.** Windows runners cannot run the Docker fixtures. **Approved 2026-11-17 (user): use the dedicated, test-only Linux server as a remote fixture host** (the user also allowed publishing database ports there, since the server holds only test data). Planned design: disposable test databases bound to `127.0.0.1` on the server, reached from the Windows runner over SSH as a `ci-tunnel` user whose key is `restrict,port-forwarding,permitopen=…` (no shell); the user adds the private key as a GitHub Actions secret. This also gives the Windows SSH tunnel (phase 4) a real target. Publishing ports directly stays a fallback. Constraints: CI fixture ports separate from the Linux port's Docker runs, no overlap with timed tests, latency-sensitive tests (cancel/expiry) may stay local-only. Set up after the Windows journal port (phase 3) passes on Windows, so the existing real-database tests run unchanged. **Built 2026-11-17:** harnesses gained `--remote` (`tools/remote-fixture.mjs`): the host still owns every container and runs every check (report, export read-back, cleanup); only the test binary runs on the client (`tools/test-remote-fixture.mjs`, CI step "Real databases (remote fixture host)", skipped without the `STONEQL_FIXTURE_*` secrets). Server: `ci-tunnel` (locked password) with a root-owned `authorized_keys` entry `restrict,port-forwarding,permitopen="127.0.0.1:*",command="/usr/local/bin/stoneql-ci-fixture"`; the forced command accepts only `<native|postgres> <40-hex commit>` and runs `/usr/local/bin/stoneql-ci-run` as `stoneql` via a single sudoers rule; it fetches that commit from the public repository and runs one harness at a time (flock). `/etc/ssh/sshd_config.d/70-stoneql-ci-tunnel.conf` (Match User ci-tunnel): local forwarding only, no listen/stream-local/tunnel/X11/agent/TTY. Verified: arbitrary commands, PTY, malformed commits, forwards to non-loopback (metadata address) and `-R` are refused; a loopback forward works. End-to-end from the Mac (macOS test binaries, temporary test key since removed): MySQL, MariaDB and PostgreSQL pass, nothing left on the host. The user's key and the three secrets are set. Run 44121992103 against the Singapore server failed one MySQL read with `DEADLINE_EXCEEDED` (3 s product read deadline; ~250 ms RTT to GitHub's US runners; the same failure reproduced from the Mac at ~290 ms to a US host), so the fixture host moved to a US VM (`136.90.29.98`, same setup and negative checks). **Run 44128236340 (2026-11-17, `86c3cf5`): MySQL, MariaDB and PostgreSQL real-database checks pass on Windows (export read-back included); 162 Rust tests pass, 0 fail; only the non-gating full `cargo audit` fails.** Cargo warns of a `stoneql_desktop.pdb` output collision (bin and lib share a name on Windows); harmless, to fix.
7. **Docs and release** only after 2–6 pass.
