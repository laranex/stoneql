### The specific cases raised

- **"The 5 s release bound cuts off a rollback; the outcome is not recorded and a later `end_transaction` returns FORBIDDEN."** **Yes, this is an unknown-outcome violation (V-1).** `release` removes the leases from the map first (882-892) and records the outcome only after `conclude` finishes inside `timeout(RELEASE_BOUND)` (896-916). The cut-off is reachable: waiting for tripped jobs (≤ 1.5 s grace) + ROLLBACK (≤ 2 s) + close (≤ 2 s) can exceed 5 s. When it is cut off, the `Physical` is dropped, so the server discards the uncommitted transaction (no false claim is made), but the outcome disappears. `end_transaction` then returns `FORBIDDEN` with `outcome: rejected` (`execution_error`), which is not `unknown`. Today's renderer never asks after disconnect or reload, so the practical impact is small, but the API contract is wrong.
- **"KILL QUERY on SLEEP() reports succeeded."** This is **acceptable for reads and for writes**. MySQL's `SLEEP()` returns 1 instead of raising 1317 when killed, so the server really did send OK. A write that completes before the kill lands has also really completed. With `interrupted=true` and `Some(Ok)` the statement is `Succeeded` (1398-1402), and the next loop iteration makes the job `cancelled` with later statements `not_run` (1382-1384). Two display gaps follow (B-11). First, pages are discarded once interrupted (`flush` 586-589), so the "succeeded" result set has missing rows and no `truncated` flag. Second, the UI then says "executed successfully". The fixture's 100-sample loop deliberately uses an erroring recursive CTE. The `SLEEP` path appears only in fault cycle 3, with no statement-status assertion. Add one.
- **Is an interrupted write always `unknown`?** **Yes**, once it was sent and did not return OK: `Some(Err) if interrupted` (1405) and `None` (1410). Reads are treated the same way (divergence 3; conservative).
- **Cancel when the KILL connection itself fails.** `send` returns false within `CANCEL_CONNECT_DEADLINE`, so `serverCancelSent=false`. The statement is still driven for ≤ 1.5 s. If it ends, its real status is reported. If not, it is `unknown`, `cancellation=requested`, and the connection is abandoned (1413-1416, 1465). This is honest. The handle permit is then released while the server may still be running the statement. The UI says "cancellation requested, not confirmed" but not "may still be running". **No test exists** (B-5).
- **SSH read-write gating.** Enforced natively, before network I/O (P8). It is not UI-only.
- **Transaction expiry/cleanup across disconnect/reset/shutdown/reload/handle expiry.** All paths call `release` (P6). Gaps: V-1 (lost outcome), B-1 (`disconnect` and the lifetime watcher release **before** removing the registry entry, so a `submit_job`/`begin_transaction` racing the multi-second release passes `writable()` and starts work that is never tripped; `reset`/`shutdown` drain the entries first and are not affected), and B-3 (the UI drops an open lease on Disconnect without a warning and never shows its outcome).

## 4. Open questions for the user (ranked by risk)

1. **The current build already enables unrestricted read-write SQL for Direct MySQL/MariaDB.** D022 requires MySQL write cancellation to be "resolved and evidenced" before that. The mechanism is implemented and evidenced on a SELECT (100/100), but no write-statement cancel (Contract 5.3) or KILL-failure case has been executed (B-5). Should read-write stay disabled in builds until B-5 passes, or is the current evidence enough for local use?
2. **SSH read-write vs the D022 alpha floor.** The alpha floor includes both SSH and CRUD, and read-write over SSH is gated off. Should the alpha ship with read-write on Direct only, or is Contract 5.2 (cancel under four busy forwards) an alpha blocker?
3. **Scripts vs single statement for the alpha (Q2).** V-2 shows that the refusal corpus for scripts can be bypassed. Keep scripts after the V-2 fix, or ship Phase A (one statement per job) first?
4. **Lost-COMMIT fault injection (B-4) as an alpha blocker?** Recommended: yes.
5. **Contract 10 values.** Every limit is PROPOSED (`ExecutionLimits`). In particular: lease idle 60 s / max 15 min, release bound 5 s, 64 job records per owner, 2 s cancel p95.
6. **Post-reload outcome reporting (Contract 4.5).** Defer with a reload warning, or implement for the alpha?
7. **PostgreSQL in the alpha**, and with it the server-side `statement_timeout` backstop (divergence 7).
8. **D003 additive-v1 posture** (an older host rejects a newer renderer's `access` field; the closed decoder is kept). Proposed as D003-M006.
9. **Metadata vendor cap** (prerequisite 7). Its exposure is unchanged by M006 but is now reachable from every read-write statement.

The builder's draft IDs "D021-E1..E10" collide with the approved D021. They are recorded as **D025-1..D025-10** in `architecture-decisions.md` (§ D025), with D003-M006 as a Proposed versioning note. Nothing beyond the D022 principles is approved.
