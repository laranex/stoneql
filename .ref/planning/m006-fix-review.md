# M006 execution safety fixes: independent review (2026-10-26)

**Status: review only. Nothing here is approved.** This is an independent check of the **uncommitted** M006 safety-fix pass (diff against HEAD `e908c49`) against the user's 2026-10-26 requirements and the earlier findings in `m006-reconciliation.md` (V-1..V-3, B-1..B-11). It is based on the code, tests and probes listed below, not on the implementer's notes. Unrelated icon, branding and docs changes in the tree were ignored. No repository file other than this one was changed. Probe code, mutants and fixture containers lived only in the session scratchpad and have been removed or stopped.

Line numbers refer to the working tree on 2026-10-26.

## Summary

- **The native gate holds.** `READ_WRITE_SQL_ENABLED = false`. Every route that can create a read-write handle passes through one check, and it refuses before Keychain or network I/O. No renderer, environment or config path can enable it.
- **V-1, B-1 and B-2 are fixed in code**, and most of their tests would fail if the fix were reverted.
- **V-2 (statement policy) is NOT fully met.** On MariaDB 11.4.8, three bypasses executed against a real server and committed a transaction that StoneQL would later report as rolled back. On SQLite, a splitter miss combined with SQLx running every statement in the text produced a false "rolled back (confirmed)" and a false "succeeded" through the real runtime.
- **V-3 (no false success) is NOT fully met for the same reason.** "Executed successfully (committed)" and "rolled back (confirmed by the server)" rely on StoneQL's model of the session's transaction state. Nothing checks that model against the server. A plain MySQL/MariaDB `CALL` outside a transaction can also break it; this was confirmed on both engines.
- **Read-write must not be enabled until blockers 1–3 below are fixed.** None of these is reachable while the gate is off.

## 2. Bypass probe results

Method: `script.rs` was compiled unchanged in a scratch harness with every input below, in and out of a lease. Server behaviour was then checked on disposable, unpublished `mariadb:11.4.8`, `mysql:8.4.6` and `postgres:17.6` containers (SQL `PREPARE` used as a stand-in for `COM_STMT_PREPARE`). The SQLite rows were run end to end through the real runtime: a probe test added to a scratch copy of the crate.

### Allowed by the policy, and they defeat transaction accounting (blockers)

| Input (accepted in and out of a lease) | Engine result | Impact |
| --- | --- | --- |
| `SET STATEMENT max_statement_time=60 FOR CREATE TABLE z(i int)` | MariaDB: implicit commit. `@@in_transaction` = 0 afterwards; a row inserted earlier **survived ROLLBACK**. `PREPARE` accepts it, so the binary path runs it | A later ROLLBACK returns OK, so StoneQL reports **"rolled back (confirmed)"** while earlier writes were committed |
| `SET STATEMENT … FOR COMMIT` | MariaDB: commits; the row survived ROLLBACK; preparable | Same |
| `SET STATEMENT … FOR CALL p()` / `… FOR TRUNCATE`, `LOCK TABLES` … | Same mechanism: the first word is `SET`, so nothing is recursed into | Same |
| `SET STATEMENT … FOR PREPARE s FROM 'COMMIT'` then `SET STATEMENT … FOR EXECUTE s` | MariaDB: both executed. Preparing the EXECUTE form returns ER 1295, so the runtime's text fallback would run it | Defeats the V-2b refusal |
| `DELIMITER //` + `CASE WHEN 1 THEN COMMIT; END CASE//` | MariaDB (compound statements are allowed outside stored programs): **committed**, row survived ROLLBACK. `CASE` raises the `Body` depth so the inner `;` is not flagged as `compound` | Same false "rolled back" |
| `DELIMITER //` + `CASE WHEN 1 THEN SET autocommit=0; END CASE//` | MariaDB: `@@autocommit` = 0 afterwards | Outside a lease, later statements in the job "succeed" and are discarded with the connection, so StoneQL reports **"(committed)"** falsely |
| SQLite: `CREATE TEMP TRIGGER rv AFTER INSERT ON parent BEGIN SELECT 1 AS begin; END; COMMIT; BEGIN; SELECT 1 AS end, 2 AS end` | Splitter: **one** statement, first word `CREATE` (the aliases `begin`/`end` move the trigger depth counter). SQLx SQLite `VirtualStatement` runs every statement in the text (`sqlx-sqlite-0.9.0/src/statement/virtual.rs` tail loop). Through the runtime, in a lease: job `Succeeded`; then `end_transaction(rollback)` returned **`RolledBack`, `rollback_sent=true`**, while the earlier row **was committed** (count 1) | False **"rolled back (confirmed)"**. Works on any granted SQLite file |
| SQLite, autocommit: same trigger trick + `BEGIN; INSERT INTO parent VALUES (78); …` | Through the runtime: job `Succeeded`; row 78 **absent** after the job (the connection was discarded with the transaction open) | False **"executed successfully (committed)"** |
| MySQL/MariaDB `CALL p()` outside a lease, where `p` does `SET autocommit=0` or `START TRANSACTION`, followed by `INSERT` | Confirmed on MySQL 8.4.6 and MariaDB 11.4.8: the INSERT reports `ROW_COUNT()=1`; **0 rows** after the session closes | False **"(committed)"**. This is ordinary usage, not an exotic input |

### Refused (correct)

`SET autocommit=0`, `SET @@autocommit=0`, `SET SESSION autocommit=0`, `SET autocommit:=0`, `` SET `autocommit`=0 ``, `` SET @@`session`.`autocommit`=0 ``, `/*!40101 SET autocommit=0 */`, `/*M!100000 …*/`, `/*!SET …*/`, `SET STATEMENT autocommit=0 FOR …`, `SET PERSIST autocommit=0`, `SET @@persist.autocommit=0`, `EXECUTE IMMEDIATE`, `XA COMMIT`, `BEGIN NOT ATOMIC …`, `IF/WHILE/FOR … COMMIT; END …` under DELIMITER (flagged `MultipleStatements`), `CALL`, `LOAD`, `ALTER TEMPORARY`, `RESET PERSIST`, `INSTALL COMPONENT` and `CREATE PROCEDURE` inside a lease, `SELECT 1 /*!99999 ; COMMIT */`, PostgreSQL `COMMIT PREPARED`, SQLite `ATTACH`/`/**/ATTACH`/`VACUUM main INTO`/`SAVEPOINT`/`END TRANSACTION`/`BEGIN IMMEDIATE`.

### Allowed, and not a transaction-accounting problem

| Input | Why it is acceptable |
| --- | --- |
| `` SET `auto` `commit`=0 ``, `SET auto/**/commit=0`, `l1: BEGIN NOT ATOMIC COMMIT; END` | The server rejects them (syntax error; checked for the labelled block) |
| MySQL `NO_BACKSLASH_ESCAPES` quote desync (`HELP 'x\'; COMMIT; -- '`) | The prepared protocol rejects multi-statement text with ER 1064 (checked on both engines), so the 1295 text fallback is never reached. **Residual:** the fallback uses `raw_sql` with `CLIENT_MULTI_STATEMENTS` advertised (`vendor/sqlx-mysql/src/connection/stream.rs:43`). A 1295-class statement that contains a string literal (routine DDL) under `NO_BACKSLASH_ESCAPES` was not probed |
| PostgreSQL `DO $$ BEGIN COMMIT; END $$`, `CALL` of a procedure that COMMITs | Inside a transaction, PostgreSQL 17.6 raises `invalid transaction termination`, so the lease becomes rollback-only (checked). Outside a lease, it is autocommit anyway. The Parse message rejects multiple commands |
| PostgreSQL `SET idle_in_transaction_session_timeout=1`, `COPY … FROM STDIN` | End as connection loss or protocol error, so the outcome is `unknown` (honest) |
| `LOAD DATA LOCAL INFILE` (outside a lease) | Inert: SQLx does not advertise `CLIENT_LOCAL_FILES` (it appears only in a parse test, `handshake.rs:110`) |
| `SELECT … INTO OUTFILE`, `SHUTDOWN`, `KILL`, `CLONE`, `RESTART`, `BINLOG`, `SET GLOBAL init_connect`, PostgreSQL `COPY … TO PROGRAM`, SQLite `PRAGMA writable_schema`/`trusted_schema=ON`/`journal_mode=OFF` | Decided by server or file privileges ("database privileges remain the authority"). They do not distort StoneQL's outcome claims. SQLite `trusted_schema=ON` undoes a hardening pragma only for that dedicated connection or lease |
| `SET completion_type=…`, `HANDLER`, `DO …`, `SIGNAL` | Do not change what StoneQL's own COMMIT/ROLLBACK report |

Aside (out of scope): the SQLite read-only path uses the same SQLx tail behaviour, and is protected by `query_only`/`READONLY`.

## 3. Test-strength assessment

- **Strong** (would fail if the fix were reverted): the gate IPC test; V-1 release-bound and record-order tests; B-2 repeat-end (runtime) and the renderer timer test; V-3 and B-6 text tests; the prepared-statement and autocommit unit corpus; `liveJobs` no-resubmit counters.
- **Partial:**

  - V-1 and transaction ends are proven on SQLite in unit tests and on MySQL/MariaDB with n=3 fixture runs only.
  - Desktop SSH read-write refusal is untested behind the gate.
- **Missing:** session-state divergence (the root cause of §2); MariaDB-specific policy cases; a SQLite single-statement assertion; PostgreSQL lost-COMMIT and write-cancel; app-close and reload with an open lease.
- **Flakiness (e):** `disconnect_racing_submit_and_begin_never_leaves_untracked_work` passed 25/25 runs in isolation and in the full suite. Residual risk is low: `refused > 0` depends on scheduling; the 20 ms sleep is unnecessary but harmless; a 5 s release-bound timeout under heavy CI load would fail the "all jobs finished" assertion. I would not class it as flaky. It is weaker than it appears (see B-1).
