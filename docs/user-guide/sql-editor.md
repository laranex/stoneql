# SQL editor

CodeMirror provides SQL highlighting, dialect-aware built-in keyword/schema completion and multiple query tabs. Use Ctrl+Space for completion and Cmd/Ctrl+Enter to execute the current query in the selected connection mode. History and query tabs belong to the active connection.

```sql
SELECT id, email FROM users WHERE id = 1 ORDER BY id LIMIT 10;
```

The mock executor supports a limited SELECT subset, including column lists, equality filters, ordering and limits. It does not execute arbitrary SQL against a database. Unsupported statements return a simulated error. Preserve SQL keywords, identifiers and raw query results when editing application text.

## Completion status

The active editor configures CodeMirror's SQL dialect and schema extension. Additional context and schema-cache helpers exist in `apps/frontend/src/sql/`, but are not wired into the active editor. Production-grade alias/JOIN resolution, ENUM-context completion and explicit backend metadata refresh are **not verified integrated features**. They require a separately scoped implementation and regression suite.

## Results

Browse-style result grids support selection, resizing and horizontal scrolling. Notifications do not own results or history; dismissing a notification leaves both intact. Editor/result and preview controls retain the existing compact workflow.

## Native read-only results

Explicit desktop Live profiles opened read-only (the default) execute a restricted single SELECT through verified TLS. No mock fallback occurs on native failure. Supported syntax is deliberately narrower than the database grammar; CALL, scripts, mutations, transaction commands and unsupported forms are refused. Live autocomplete metadata is not implemented. MySQL/MariaDB live profiles list tables and browse them read-only (see [Connections](./connections.md)); the editor does not yet use that catalog.

Results retain ordered columns, including duplicate labels, exact integer/decimal strings, raw temporal text, NULL and hexadecimal binary/unknown values. Limits are 1,000 rows, 1 MiB serialized result and 2 MiB per incoming protocol packet; truncation is labelled, while an oversized individual value fails rather than being silently shortened. A three-second native deadline is not confirmation of server cancellation. Errors use safe fixed messages and do not expose raw driver diagnostics. There is no automatic SQL retry.

## Native read-write execution

Direct desktop Live connections are **read-write** by default (approved 2026-11-17, A15). Tick **Read-only connection** in the connection dialog to open that connection read-only instead; the choice is saved with the connection. SSH Tunnel connections are always read-only for now (SSH read-write awaits a separate approval). PROD-tagged profiles ask for the "PROD — I understand" acknowledgement each time they connect read-write. The badge next to the connection shows **Read-only** or **Read-write**.

In read-write mode **Run query** executes the editor content as a script, one statement at a time, stopping at the first statement that does not succeed. Scripts containing `DELETE`, `UPDATE`, `DROP`, `TRUNCATE`, `ALTER`, `REPLACE`, `RENAME`, `GRANT` or `REVOKE` ask for confirmation first. These confirmations are safeguards, not permissions: the database account decides what is allowed. If the connection is already running something, the request is refused (nothing is queued or sent).

- Each statement shows **succeeded**, **failed**, **unknown** or **not run**. A failure names a constraint kind and SQLSTATE when the database reports one; the database's own message is withheld because it can contain row values.
- Every result set is kept; use the **Result N · statement M** tabs to switch. Large results are delivered in pages and bounded (1,000 rows per result set by default, 1 MiB per result set, 4 MiB per run); truncation is labelled.
- **Cancel** requests a best-effort server interrupt. The result says whether the stop was confirmed; a statement interrupted after it was sent is **unknown**, because its effects cannot be excluded. Verify on the server; StoneQL never re-runs it.
- On PostgreSQL each statement has a server time limit set just below StoneQL's own statement deadline. A statement that reaches it is stopped by the server and shown as **failed** at the statement time limit (SQLSTATE 57014); inside a transaction only Rollback is then offered. If the server limit does not stop it, StoneQL's deadline interrupts it and the outcome is **unknown**.
- Without a transaction, each successful statement is committed immediately (autocommit). A run is reported as succeeded only after StoneQL checked that the session was still in autocommit with no open transaction; otherwise the outcome is unknown. **Begin transaction** runs later scripts in one transaction until **Commit** or **Rollback**. After a failed or interrupted statement only Rollback is offered. A transaction ends after 60 seconds idle or 15 minutes open, or when the connection closes; StoneQL then attempts a rollback, and the outcome (rolled back or unknown) is shown on the next Commit, Rollback, Disconnect or run; a run on a transaction that has already ended sends nothing and says why it ended (for example that it expired after being idle). Commit and rollback are reported as done only when the server confirms them; otherwise the outcome is shown as unknown.
- If the connection fails, or a run ends failed, cancelled or unknown, the result never says "executed successfully"; it states which statement ended how. A Commit or Rollback that is not confirmed in time is shown as **outcome unknown** (with whether COMMIT or ROLLBACK may have been sent), never as committed or rolled back.
- **Disconnect** with an open transaction asks first; the transaction is then rolled back and its confirmed or unknown outcome is shown, also when the disconnect itself fails.
- Closing StoneQL while a transaction is open or a read-write statement is running asks first. Closing ends that work, and its outcome is not shown afterwards; verify on the server.
- **Outcome unknown — the server may or may not have applied it.** Every unknown outcome (a run or a transaction end) is also listed in a red panel above the workspaces, with the connection's database name, until you choose **Acknowledge**. Acknowledging only hides the entry after you have checked the server; it never marks the work as done or undone. The list survives reloading StoneQL (entries from before a reload are labelled "Before a reload"; a statement still stopping during the reload is added by itself once its outcome is known) and quitting or a crash: StoneQL saves each unknown outcome to a private file on your Mac before it sends the work, and lists it after the next start labelled "Before a restart". A transaction that was still open, or a run still in progress, when StoneQL quit or crashed is listed the same way ("was still open when StoneQL quit or crashed"). The file holds no SQL, values or passwords. If StoneQL cannot save that file (for example, the disk is full or the folder's permissions are wrong), or finds it damaged, the panel says so and StoneQL refuses new read-write runs and transactions, and COMMIT, until it can save again; read-only queries and rollback still work. A damaged file is kept beside it, never deleted. On macOS, if the page itself crashes, StoneQL ends its open work the same way and reloads. While 16 unknown outcomes are unacknowledged, StoneQL starts no new read-write run or transaction and sends nothing; an open transaction can still be committed or rolled back.
- Use the transaction buttons instead of `BEGIN`, `COMMIT`, `ROLLBACK`, savepoints or autocommit changes (anywhere in a `SET`), which are refused in scripts. MySQL/MariaDB `PREPARE`, `EXECUTE`, `DEALLOCATE`, `CALL`, MariaDB `SET STATEMENT … FOR` and compound statements (`CASE`, `IF`, loops, labelled blocks) outside a stored program are refused too, as is a second statement hidden behind a custom `DELIMITER`. Inside a MySQL/MariaDB transaction only `SELECT`, `WITH`, `VALUES`, `TABLE`, `SHOW`, `DESCRIBE`, `EXPLAIN`, `INSERT`, `UPDATE`, `DELETE`, `REPLACE`, `USE`, `SET @variable` and `CREATE`/`DROP TEMPORARY TABLE` run. SQLite `ATTACH`, `DETACH` and `VACUUM INTO` are refused, and a SQLite statement runs only if SQLite parses it as exactly one statement.

See [read-write SQL execution](../development/sql-execution.md) for the full behaviour and limits.
